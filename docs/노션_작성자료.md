# 노션 보고서 작성 자료

노션 페이지의 빈칸에 옮겨 적을 내용을 칸 이름 그대로 모아 둔 문서다. 표로 된 칸은 노션 표에 그대로 옮길 수 있게 표로 적었다. "직접 작성"이라고 표시한 칸은 조원이 실제로 한 일과 느낀 점을 적어야 하는 곳이라 비워 두었다.

노션의 역할 분담표에는 "사용한 AI"가 ChatGPT로만 적혀 있다. 개발에는 Claude Code를, 서비스 안의 챗봇에는 OpenRouter 무료 모델을 썼으므로 그 칸도 함께 고쳐야 4-1, 4-5와 내용이 맞는다.

## 맨 위: 노션배포주소

노션 페이지를 웹에 게시한 뒤 그 주소를 적는다. (직접 작성)

## 4-3. 화면 구성 / 동작 흐름

화면은 로그인·가입, 홈(모임 목록), 모임 만들기, 모임 상세, 추천(챗봇), 내 모임 여섯 가지다. 와이어프레임 자리에는 5-1에서 찍을 실행 화면 가운데 홈, 모임 상세, 챗봇 세 장을 나란히 넣으면 된다.

이용자 흐름:

```
[가입·로그인]
      ↓
[홈: 열려 있는 모임 목록 + 나를 위한 추천]
   ↙            ↓               ↘
[만들기]     [검색·필터]      [추천 챗봇에 문장으로 질문]
   ↓            ↓               ↓
[모임 등록]  [모임 상세 확인]  [조건 해석 → 맞는 모임 카드]
   ↓            ↓               ↓ (없으면 대안 또는 '이 조건으로 직접 열기')
[참여자 모집]  [참여 → 선착순 확정] ←┘
      ↘        ↙
   [정원이 차면 자동 마감 → 오픈채팅으로 연락 → 모임]
```

챗봇 내부 흐름:

```
사용자 문장
   ↓
① 문장 → 조건(날짜, 시각, 소요 시간, 종류, 키워드)
   · OpenRouter 무료 모델이 해석
   · 키 없음 / 한도 초과 / 응답 지연이면 규칙 기반 해석기로 대체
   ↓
② 서버가 조건 값을 검증(허용된 종류·시간 형식만 통과)
   ↓
③ 서버가 DB에서 열려 있는 모임을 고르고 점수 계산
   ↓
④ "이렇게 이해했어요" + 모임 카드 + 추천 이유 표시
```

## 4-4. 핵심 코드 설명

### (1) 조건에 맞는 시간인지 판정하는 코드 — `bungae/recommend.py`

```python
def time_fit(meeting, cond):
    """('fit' | 'near' | 'miss' | 'none', 설명)"""
    if not cond.has_time:
        return "none", None
    near_reason = None

    if cond.max_duration_min and meeting.duration_min > cond.max_duration_min:
        over = meeting.duration_min - cond.max_duration_min
        if over > NEAR_MINUTES:
            return "miss", None
        near_reason = f"{over}분 더 걸려요"

    if cond.window_start and meeting.start_at < cond.window_start:
        return "miss", None

    if cond.window_end:
        if cond.must_end_in_window:
            over = int((meeting.end_at - cond.window_end).total_seconds() // 60)
            if meeting.start_at >= cond.window_end or over > NEAR_MINUTES:
                return "miss", None
            if over > 0:
                near_reason = f"{over}분 늦게 끝나요"
        elif meeting.start_at >= cond.window_end:
            return "miss", None

    if near_reason:
        return "near", near_reason
    return "fit", "시간이 맞아요"
```

이 코드가 하는 일: 사용자가 말한 시간 구간과 모임 시간을 비교해 "맞음 / 거의 맞음 / 안 맞음"을 가린다. "2시간 비는데"처럼 빈 시간을 말한 경우(`must_end_in_window`)에는 모임이 그 안에 끝나야 하고, "저녁에"처럼 막연한 시간대를 말한 경우에는 그 안에 시작하기만 하면 된다.

왜 이렇게 만들었나: 처음 기획에는 모임 정보에 시작 시각만 있었는데, 그러면 "2시간 빈다"는 말과 맞춰 볼 수가 없어서 예상 소요 시간을 모임 정보에 추가했다. 또 딱 맞는 모임만 보여 주면 결과가 비기 쉬워서, 30분 이내로 넘치는 모임은 "30분 늦게 끝나요"라는 설명을 붙여 후보로 남겼다. 이 판정은 언어 모델이 아니라 코드가 하므로 같은 질문에는 항상 같은 결과가 나온다.

### (2) 모델의 답을 검증하는 코드 — `bungae/nlu.py`

```python
def sanitize_slots(raw, today):
    """바깥에서 온 값(모델 출력, 세션 쿠키)을 믿지 않고 형식에 맞는 것만 남긴다."""
    slots = empty_slots()
    if not isinstance(raw, dict):
        return slots
    ...
    value = raw.get("categories")
    if isinstance(value, list):
        slots["categories"] = [key for key in CATEGORY_KEYS if key in value]
    ...
    return slots
```

이 코드가 하는 일: 언어 모델이 돌려준 JSON에서 날짜, 시각, 소요 시간, 종류, 키워드를 하나씩 꺼내 형식이 맞는 것만 남긴다. 종류는 미리 정한 여덟 가지 안에 있는 것만, 날짜는 오늘부터 14일 안의 것만 통과한다.

왜 이렇게 만들었나: 언어 모델은 가끔 형식을 어기거나 없는 값을 만들어 낸다. 모델의 답을 그대로 DB 검색에 쓰면 오류가 나거나 엉뚱한 결과가 나오므로, 모델을 "믿을 수 없는 외부 입력"으로 취급했다. 같은 이유로 모델에게는 사용자의 문장만 보내고 모임 목록은 보내지 않는다. 어떤 모임을 추천할지는 서버 코드가 DB에서 직접 고르기 때문에 모델이 없는 모임을 지어낼 수 없다.

### (3) 마지막 한 자리 동시 신청을 막는 코드 — `bungae/meetings.py`

```python
meeting = db.session.execute(
    select(Meeting).where(Meeting.id == meeting_id).with_for_update(of=Meeting)

...
elif not meeting.joinable:
```

이 코드가 하는 일: 참여 버튼을 누르면 먼저 그 모임의 행을 잠그고, 그 상태에서 현재 인원을 세어 자리가 있을 때만 참여자를 추가한다.

왜 이렇게 만들었나: 한 자리 남은 모임에 두 사람이 거의 동시에 참여를 누르면, 둘 다 "자리 있음"을 확인한 뒤 둘 다 추가되어 정원을 넘길 수 있다. 잠금을 걸면 두 번째 사람은 첫 번째 사람의 처리가 끝난 뒤에 인원을 세게 되어 "마감"으로 처리된다.

## 5-1. 실행 화면

테스트 과정에서 실제로 잡힌 문제도 보고서에 쓸 수 있다. 처음 돌렸을 때 708개 가운데 36개가 실패했고, 원인은 대부분 한국어 시간 표현 해석이었다. 예를 들어 "다음 주 월요일"을 한 주 더 뒤로 계산했고, "1시간 30분 뒤"를 30분 뒤로 읽었으며, "5시 전"을 "5시 이후"로 반대로 해석했고, 이미 지난 시각을 말하면 검색 구간의 시작이 끝보다 늦어졌다. "99999999시간 뒤"나 0001년 날짜를 넣으면 서버 오류(500)가 나는 문제도 있었다. 모두 고친 뒤 다시 돌려 전부 통과했다.

테스트로는 드러나지 않고 코드 검토에서만 나온 문제도 있었다. 배포용 PostgreSQL 주소를 넣으면 드라이버를 찾지 못해 앱이 뜨지 않는 문제가 대표적이다. 로컬과 테스트는 SQLite만 쓰기 때문에 716개가 모두 통과하는 상태에서도 숨어 있었다. "테스트 통과가 곧 배포 가능을 뜻하지는 않는다"는 사례로 발표에 쓸 수 있다.

브라우저에서 직접 확인한 항목(로컬, 예시 데이터 기준): 로그인, 홈 목록과 종류 칩 필터, 모임 상세의 겹침 경고와 댓글, 화면 아래에 고정된 참여 버튼, 참여 후 인원 변화(2/4명 → 3/4명), 내 모임과 계정 설정, 만들기 폼 미리 채움, 공유 링크로 들어와 가입한 뒤 그 모임으로 돌아오는 흐름, 알림함, 챗봇 질문과 이어 묻기.

실제 OpenRouter 키를 넣고 확인한 항목(로컬, 2026-11-13 낮 12시 40분쯤, 예시 데이터 기준). 이 부분은 자동 테스트가 아니라 실제 모델이 답한 결과다.

| 테스트 항목 | 입력 | 기대 결과 | 실제 결과 | 통과 |
|---|---|---|---|---|
| 실제 모델 해석 | "내일 점심 먹고 나서 두 시간쯤 비는데 조용히 공부할 사람 있어?" | 내일, 2시간 이내, 공부로 해석하고 "AI 해석" 표시 | 내일 · 2시간 이내 · 공부 · #조용히, "AI 해석" 표시 | O |
| 실제 모델 이어 묻기 | 위 질문 뒤 "그럼 카페는?" | 시간 조건은 유지하고 종류만 카페로 | 내일 · 2시간 이내 · 카페·수다 · #조용히 | O |
| 실제 모델 잡담 | "안녕! 넌 뭐 하는 애야?" | 서비스 소개와 질문 예시 안내 | "번개팟구예요. '오늘 3시부터 2시간 비는데…'처럼 말씀해 주시면…" | O |
| 기본 모델이 막힌 경우 | 기본 모델(Gemma)이 제공사 쪽에서 429를 돌려주는 상태 | 대체 모델이 답하거나 규칙 기반으로 전환 | 대체 모델이 답함. 처음 넣은 Nemotron은 6~11초, 측정 뒤 바꾼 Flint는 4~7초. 대체 목록을 넣기 전에는 규칙 기반 "기본 해석"으로 전환됨 | O |

같은 문장을 규칙 기반 해석기에 넣으면 "점심"을 시간대로, "먹고"를 식사로 읽어 "내일 11:30~13:30 · 식사 · 공부"로 해석한다. 모델은 "점심 먹고 나서"를 식사 모임이 아니라 그 뒤의 빈 시간으로 이해했다. 규칙으로는 잡기 어려운 표현에서 언어 모델이 주는 차이를 보여 주는 예로 발표에 쓸 수 있다.

실제 호출에서 문제도 두 가지 나왔다. 고른 무료 모델이 우리 키의 사용량이 0인데도 제공사 쪽에서 일시적으로 막혀 있었고(429), 다른 무료 모델로 바꿔 보니 답이 비어서 왔다. 뒤의 것은 추론형 모델이 답을 쓰기 전 '생각'에 토큰 한도 500을 다 써 버렸기 때문이었다. 대체 모델 목록을 두고 한도를 2,000으로 올려 해결했다.

대체 모델은 측정해서 골랐다. 같은 문장 두 개를 후보 모델에 보내 응답 시간과 해석이 맞는지를 봤다. Nemotron은 6초에서 38초까지 들쭉날쭉했고 한 번은 생각만 하다 답을 못 냈다. ERNIE는 3초로 가장 빨랐지만 세 번 중 한 번 같은 식으로 실패했다. Flint는 4~7초로 일정했고 해석이 모두 맞았다. 그래서 Flint를 첫 번째, ERNIE를 두 번째 대체 모델로 두었다. 추론을 끄거나 줄이는 설정도 시험했지만 Flint와 ERNIE는 끌 수 없었고 줄여도 빨라지지 않았다.

## 6-1. 목표 달성도

2장에서 정한 최종 아이디어는 "호스트가 번개 모임을 만들고 게스트가 참여하는 기능을 기본으로, 원하는 시간과 관심 조건에 맞춰 열려 있는 모임을 추천한다"였다. 모임 생성·참여·자동 마감, 조건 검색, 관심사 기반 추천, 문장으로 묻는 추천 챗봇까지 구현해 기획한 범위는 모두 동작한다. 처음 정의한 문제 가운데 "현재 참여 가능한 모임의 시간, 인원, 분위기를 한눈에 파악하기 어렵다"는 부분은 목록과 상세 화면, 추천으로 해결했다. 반면 "실제로 함께할 사람을 빠르게 찾게 되는가"는 사용자가 모여야 확인할 수 있는 부분이라 이번 프로젝트에서는 검증하지 못했다. (조의 판단에 맞게 고쳐 쓴다)

## 6-2. 한계점과 개선 방향

- 숭실대 학생 인증을 이메일 형식으로만 확인한다. 인증 메일을 보내 실제 소유자인지 확인하는 절차가 필요하다.
- 참여는 선착순 자동 확정만 된다. 호스트가 신청자를 승인하는 방식과 대기 신청을 추가할 수 있다.
- 알림은 사이트에 들어와야 볼 수 있다. 휴대폰 알림이나 메일로 보내 주지는 못한다.
- 참여자끼리의 대화는 서비스 밖 오픈채팅에서 이루어져, 그 안에서 생기는 문제를 서비스가 알 수 없다. 다른 모임 서비스들은 이 때문에 앱 안 채팅을 쓴다.
- 무료 언어 모델은 제공사 사정으로 수시로 막히고, 대체 모델이 답할 때는 4~7초가 걸린다. 빠르고 안정적인 응답이 필요하면 유료 모델을 써야 한다.
- 무료 언어 모델의 하루 한도(50회) 때문에 사용자가 늘면 챗봇 대부분이 규칙 기반 해석으로 처리된다. 규칙 기반 해석기는 "3교시 끝나고", "주말에" 같은 표현을 알아듣지 못한다.
- 비밀번호를 잊었을 때 다시 설정하는 기능이 없다. 메일을 보낼 수단이 없어서다.
- 신고는 3명이 쌓이면 모집을 자동으로 멈추는 데까지만 한다. 한 번 멈춘 모임을 다시 풀어 주는 절차도 없다. 사람이 내용을 확인하는 절차, 특정 사용자 차단, 노쇼 방지 장치가 없다.
- 설문이나 인터뷰로 수요를 확인하지 못했다. 시범 운영으로 실제 사용 조건을 조사할 필요가 있다.
